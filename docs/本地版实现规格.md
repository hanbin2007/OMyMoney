# 钱迹本地版独立重写规格

状态：用户已认可，进入实施计划。基准：用户提供的 Android APK 4.5.3b7，versionCode 1229。本文定义要实现的产品及验收边界，不代表 App 已经完成。

## 已确认目标

- 不是只做自动记账工具，而是整款 App 的个人本地版：账户、账本、预算、统计以及其他本地功能均纳入范围。
- **UI 全面采用 Material Design 3 / Material You，UX 以自然、可预期、高效且可恢复的 Android 交互为要求。** 功能和账务行为参照原版，但不照搬与 M3 规范冲突的旧界面；本条替代此前的逐像素外观复刻方向。
- 原生 Kotlin 独立重写，不修改重签原 APK，不连接原服务端，不复用原账号凭据。
- 数据保存在本机；登录、云同步和多人账本暂不实现。
- **本期不接本地 AI，也不接云端 AI，只预留接入接口。** 不下载模型、不常驻推理引擎、不制造“AI 已识别”的假结果。
- 用户只限定为现代 Android 手机，未指定机型。系统兼容基线暂采用原 APK 的 Android 8.0 起，较新系统的后台行为需要独立验证。

产品名称“OMyMoney”，独立包名 `app.omymoney.android`，项目目录 `PROJECT_ROOT`。可与原版并存，不覆盖原版数据。名称和图标不冒充钱迹官方；在功能完整的前提下，按 M3 重新组织界面与交互。

## 方案选择

采用 Kotlin、Jetpack Compose 与官方 Material 3 组件、独立账务核心、Room 本地数据库和 Android 系统能力。替换此前以 Views/XML 为主的 UI 方案；系统服务、通知及小组件继续使用合适的原生接口，不强行把所有系统表面塞进 Compose。

与修改重签原 APK 相比，独立重写可以去除对原后端、权益验证和未知 SDK 的依赖，维护代码也可审计；代价是必须逐项还原行为。与跨平台 UI 加原生插件相比，原生方案更直接承载无障碍、前台服务、悬浮窗、小组件和原版交互。

不承诺从静态 APK 自动恢复完整源代码。完成标准是明确的功能与视觉对照测试，不是“反编译成功”或“安装后有一个类似首页”。

## 架构与数据流

采用四个清晰边界，不提前建立微服务或插件系统：

| 边界 | 职责 |
| --- | --- |
| 账务与识别核心 | 金额、账单类型、余额影响、预算统计口径、页面匹配、字段提取、去重规则；能在 JVM 上测试 |
| 本地数据层 | Room 实体、事务、查询、迁移、附件、备份恢复和导入导出 |
| Android 接入层 | 无障碍、悬浮窗、前台通知、权限、OCR、周期任务、小组件、文件选择与分享 |
| 原生界面层 | 页面、表单、导航、错误状态、草稿编辑、主题；不在 View 中重复计算账务 |

手工记账、自动记账和导入最终都进入同一账单校验与保存入口。账户变动、关联退款或报销记录及保存状态在事务中一起更新，失败时不留下半笔账。

### 数据约束

- 金额使用精确十进制规则，持久化金额以整数与精度表示，不把二进制浮点作为账务真值。
- 时间区分交易时间、识别时间、保存时间与账务日期。识别不到交易时间时保留“未知”，不将识别时刻冒充交易时刻；人工可确认补齐。
- 账单标记来源及识别规则版本，区分已识别、待确认、已保存、已忽略和失败。
- 转账必须使用不同的转出与转入账户；手续费和汇兑差额独立处理，避免统计为普通消费两次。
- 修改或删除账单必须撤销旧余额影响再应用新影响；退款与报销关联不能悬空。
- 预算、报表与列表使用同一查询口径，尊重“不计统计”和“不计预算”的区别。
- 本地 ID 独立生成，不假装属于原版账号；不尝试直接覆盖原版私有数据库。

## 自动记账

### 采集边界

用户主动授权后，只处理已启用应用的交易页面。优先解析无障碍节点，不自动点击付款、转账或确认按钮，不采集密码字段，不绕过系统或支付应用的安全限制。

保留开启和暂停操作及可见服务状态。权限撤销、系统回收或读取失败时停止采集并呈现可恢复状态，不能通过后台偷偷重开权限。

### 规则覆盖

本次静态分析确认：监听配置有 11 个包名，实际页面适配器有 7 个，57 个页面匹配器与 58 个提取器中有 56 个连接起来的提取场景。

先以这 56 个可达场景建立独立规则与测试索引，覆盖微信、支付宝、拼多多、云闪付、京东、美团和抖音。淘宝两个未接入的提取器不计入已可用覆盖；微信密码页匹配器不作为账单场景。第三方 App 的版本适配以样本和真机结果为准，不以类名存在作为支持证据。

处理步骤：

1. 服务开关与包名过滤，检查交易页面。
2. 事件合并与延迟调度，构建受限的节点快照。
3. 页面匹配和字段提取，保留原文字段依据。
4. 金额、时间、类型及支付状态校验；冲突字段留待确认。
5. 去重，生成或合并候选草稿。
6. 本地账户匹配；分类使用明确规则或最近人工选择，不称为 AI 判断。
7. 显示悬浮确认窗口，支持编辑、保存、忽略。
8. 用户保存成功后才增加已入账计数，并通过统一入口写库。

### 去重与差异

原版的最近事件标记、无时间账单一小时缓存、数据库前后 60 秒相似账单检查均建立兼容测试。默认把同金额同时间当作相似候选，而非在缺少商户或订单依据时强行认定同一笔。

保留忽略提示、弹窗确认、跳过去重三种用户选择，明确“跳过去重”不等于无确认静默保存。

独立重写有两个有意修复点，必须记录为差异：悬浮窗口打开时将新草稿排队，而非丢弃；识别失败、取消和保存分别记状态，不把识别次数伪装为入账次数。

## 无 AI 与未来接口

### 本期实际行为

- 已知支付页面继续用规则识别金额、时间、商户和交易类型。
- 账户用精确名称、银行卡尾号、相似描述和来源场景匹配；多候选时让用户选择。
- 分类保留手动选择和明确的本地映射，不声称具备开放式语义理解。
- 截图先运行打包的本地中文 OCR，再用已知模板提取；无法确定的金额、日期和类型留空或标记待核对，不补造一笔账单。
- 不出现不可用的 AI 开关、假进度或模型下载入口。

### 接入契约

预留一个可选的识别增强接口，不引入模型 SDK。输入为最小必要的脱敏文本、已有字段与证据、允许选择的账户和分类、超时及取消信号；输出仅为字段建议、对应原文依据、候选 ID 和失败原因。

默认实现返回“不提供增强”，现有流水线照常运行。未来端侧或云端实现都必须通过相同业务校验，不直接访问数据库，不发起付款，不覆盖用户已经手工修改的字段，也不把返回的置信度直接当作可靠性保证。

接口适配测试包括：未安装提供方、超时、取消、非法 JSON 或字段类型、不存在的账户分类、金额与原文矛盾、迟到结果。这样以后接 AI 不需要重写账单保存流程。

## Material Design 3 与 Material You

“完整 M3”指设计系统和实际组件行为一致，不是仅替换主题颜色，也不是为了展示组件而把每一种组件都加入 App。实施前仍需运行原版建立功能和状态清单；原版截图用于避免漏掉业务操作，不作为新界面的逐像素目标。

### 主题与设计系统

- 使用官方 `androidx.compose.material3` 组件，统一颜色角色、文字样式、形状、间距、层级、状态与动效。禁止混搭 M2 默认控件、网页式仿制控件或每页自定义一套按钮。
- Android 12 及以上默认支持 Material You 壁纸动态取色；提供动态色开关。关闭动态色或旧系统使用完整的固定浅色与深色方案。主题可跟随系统、浅色、深色。[官方主题文档](https://developer.android.com/develop/ui/compose/designsystems/material3)
- 内容通过语义角色取色，不散落硬编码色值；收入、支出、转账、错误同时有文字或符号区分，不只靠红绿颜色。
- 文字使用 M3 的标题、正文和标签层级，金额使用清晰稳定的数字排版。字体跟随系统缩放，字间距统一为 0；不按屏幕宽度整体缩放字号。
- 圆角与阴影使用相应 M3 组件规范，不给所有内容包一层大圆角卡片，也不嵌套卡片。账单、账户、设置以列表和明确分区为主。
- 图标采用统一的 Material 图标资源，图标按钮有无障碍名称；不熟悉的图标提供标准提示，不手绘相似但语义模糊的符号。
- 顶栏、底部导航、导航轨、FAB、按钮、输入框、菜单、对话框、底部面板、选择器、Switch、Checkbox、FilterChip、Snackbar 和进度反馈按用途选择，覆盖可用、按下、聚焦、选中、禁用、加载与错误状态。
- 动效只服务于状态反馈、层级变化和空间连续性，允许中断，尊重系统减少动画设置；不用动画延迟保存反馈或阻止快速连续操作。

### 信息架构

手机主导航固定为“账单、资产、统计、设置”。账本切换位于相关页面顶栏，当前账本始终可辨识。预算在统计页有固定入口，账单页也可直接查看当前预算摘要；自动记账设置在设置页固定位置，运行时通知提供暂停和恢复。

记一笔是主操作，使用 FAB；搜索、日期筛选和更多操作使用常见图标与菜单。进入账单详情可直接编辑；退款、报销等关联操作保留在对应详情上下文，避免用户在无关页面重新寻找原账单。

较大窗口采用 M3 导航轨及合适的列表详情布局，不把手机页面简单拉宽。页面遵守系统栏、刘海、手势区域和键盘 Insets，不为沉浸效果遮挡操作。

## UX 行为契约

“符合人类习惯”落实为以下可验证要求，不以主观的“绝对完美”代替测试。

| 用户任务 | 交互约束 |
| --- | --- |
| 首次使用 | 直接进入可用本地账本；创建默认本地账本和基础分类，不强迫注册或一次性申请所有权限 |
| 记一笔普通支出 | 打开记账后可立即输入金额；分类、账户、日期在同一工作流内完成；保存按钮在键盘出现时仍可达 |
| 切换收入或转账 | 使用分段控件；保留合理共用字段，对不兼容的账户和分类明确处理，不悄悄改变交易含义 |
| 选择分类和账户 | 用可搜索的单一选择面板；当前值有明确选中态；避免多层弹窗叠加和只能靠长按发现的关键操作 |
| 校正识别结果 | 先显示识别到的金额、时间、来源和未确定字段，用户可直接修改；异步更新不能覆盖已经手工编辑的值 |
| 遇到重复账单 | 同屏展示新草稿与已记录账单的关键差异，提供“忽略”和“仍然记录”；不只给一个无法理解的错误提示 |
| 连续收到草稿 | 显示待确认数量，当前输入不被新弹窗打断；逐笔处理或稍后返回，不抢键盘焦点 |
| 返回和中断 | 系统返回先关闭当前键盘或选择面板，再返回上一层；草稿可恢复，有输入时不能无提示丢弃；支持平台返回手势 |
| 删除 | 普通可恢复删除提供 Snackbar 撤销；清空、批量删除和覆盖恢复先说明影响并确认，不隐藏在单次滑动中 |
| 保存 | 校验问题定位到字段并保留输入；提交防连点；写库成功后立即反馈并回到合理位置，失败不清空表单 |
| 切换账本或筛选 | 不丢失列表位置和合理的页面状态；当前过滤条件可见且可清除，不让空结果看起来像账单被删除 |
| 开启自动记账 | 在使用时解释并请求权限；从系统设置返回后重新检查真实状态；拒绝权限仍能手工记账 |
| 导入和恢复 | 先预览数量及冲突，再由用户确认；有进度、取消边界和结果报告；失败不得破坏已有数据 |

常用字段可以记住上次选择，但账本、收支方向和资产账户必须始终可见。高风险操作不能只依赖颜色、手势或用户记忆。错误消息用具体中文说明问题及下一步，不直接暴露栈追踪，也不提供无效重试按钮。

### 可访问性与适配

- 所有独立点击目标至少 48 x 48 dp，触控区域之间不得重叠；不能把图标的视觉大小当作完整触控目标。[Android 可访问性文档](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)
- TalkBack 有正确的控件角色、名称、值和状态；图表提供可读汇总和数据列表，装饰图标不重复朗读。
- 校验普通文本与背景至少 4.5:1、大文本至少 3:1 的对比度；动态颜色和深色模式分别检查，不仅检查固定主题。
- 检查 200% 字体缩放、较大显示缩放、长商户名、大金额、小数与负数，内容不遮挡保存按钮、不被关键位置截断。
- 支持键盘焦点和合理焦点顺序；焦点、选中和禁用状态可区分，不把长按作为唯一入口。
- 全程不使用只有颜色变化才可识别的错误或成功状态。

### UX 验收方法

以新增、编辑、撤销删除、转账、退款、预算调整、识别校正、权限拒绝、截图失败、备份恢复这些真实任务做走查和自动化测试。每个任务至少验证正常路径、返回或取消路径、错误恢复路径。

截图覆盖紧凑和大屏、浅深色、动态色开关、字体放大、空数据与长列表。Compose 语义测试检查控件可操作性，实际设备或模拟器检查触控、输入法、TalkBack、返回手势和悬浮窗口。重要 UI 完成后进行独立 UX 与可访问性审查，有严重阻断问题不通过验收。仅使用 M3 组件不能自动证明 UX 合理。

## 隐私与错误处理

- 本地版不申请网络权限，不加入原版分析统计、广告、云同步或远程 AI SDK。
- 截图留存默认关闭；用户主动附图时只保存在应用私有目录。一般识别日志默认不保存完整页面文本或银行卡信息。
- 权限、OCR、解析或模型预留接口失败都回到可编辑草稿或明确失败状态，不影响既有账目。
- 备份由用户主动选择位置；导出前明确数据敏感性。恢复先校验格式和完整性，再以事务导入，失败不覆盖现有数据库。
- 大量事件有队列上限、取消和过期机制；只有账单成功提交后才产生最终余额影响。
- 不将上传、识别、生成草稿、保存、同步等不同状态混写为“完成”。

## 实施阶段

1. **原版功能基线与账务基础**：页面和操作清单、M3 设计系统与导航、测试数据、数据库、账本分类账户、完整手工记账与余额正确性。先得到真实可用的本地记账闭环。
2. **自动记账闭环**：节点模型、规则索引、去重、账户匹配、草稿队列、权限与悬浮确认、离线 OCR，以及不依赖模型的增强接口。
3. **其余本地能力**：预算、统计、退款报销借贷、周期分期、存钱计划、导入导出、主题隐私锁、小组件；逐项补齐原版对应行为。
4. **整体验收**：M3 一致性和真实任务 UX、原版功能对照、数据一致性、恢复与迁移、后台和权限异常、兼容性与性能；整理已实现、已验证、已知差异及未验证项。

原始 APK 中存在的复杂账务类型必须纳入整体数据模型，但首阶段只启用完成验证的入口，避免用不完整实现影响余额。后续阶段不能跳过独立验收就把整个项目标为完成。
