# 钱迹 4.5.3b7 自动记账静态分析

分析对象是用户提供的 `qianji_453b7_1229_beta.apk`，不是应用商店中的其他版本。目标已经确认：独立实现整款 App 的个人本地版，功能参照原版，UI 改用完整 Material Design 3 / Material You，登录、云同步和多人账本后续另建。

当前范围更新：本期不接本地或云端 AI，只预留识别增强接口；已知页面规则、本地账户匹配和离线 OCR 继续纳入实现。

**当前结论：自动记账主链路已经定位，但不是完整复刻完成。** 此版本主要通过无障碍页面节点识别交易，然后进行去重、账户匹配，弹出可编辑的记账窗口，保存后进入账务数据库。AI 分类和截图转账单另有服务端依赖，APK 不包含服务端模型、提示词或完整服务实现。

## 主链路

```text
用户开启无障碍服务与所需权限
    -> 窗口变化或窗口内容变化事件
    -> 总开关、权益、应用包名、页面过滤
    -> 按应用延迟处理，进入单线程执行器
    -> 遍历同一窗口的无障碍节点
    -> 按优先顺序匹配页面类型
    -> 页面专用提取器生成 BillInfo
    -> 无时间账单缓存去重、最近事件标记去重
    -> 可用时尝试截图，截图失败仍继续
    -> 应用内定向广播 GET_BILL_INFO
    -> 前台悬浮窗服务
    -> 查询已入库的相似账单
    -> 本地账户匹配，或 AI 匹配后失败回退本地
    -> 用户编辑、保存或取消
    -> 数据库保存、账户处理、日志、界面刷新
```

这里的“自动”不能直接理解成“所有交易都在后台静默落库”。已定位的无障碍主链路会显示记账确认窗口；识别计数是在广播分发后递增，早于用户实际保存，所以识别成功、弹窗成功和入账成功必须分开记录。

### 事件入口和调度

- 服务类为 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`。虽然名称位于类似 Google 的包路径，它是当前 APK 内分析到的服务类，不能因此认定其来自 Google。
- XML 配置只订阅 `typeWindowStateChanged` 和 `typeWindowContentChanged`，`notificationTimeout=10`，允许读取窗口内容、报告 viewId、访问交互窗口和截图。
- 主链路使用 `AccessibilityEvent.getSource()`，随后在同一 `windowId` 下进行深度优先遍历，不是直接访问微信或支付宝的私有数据库。
- 支付宝安排 160 ms 快速轮次和 450 ms 回退轮次；快速轮次仅继续处理 `AlipayPaySuccess`。
- 微信安排 150 ms；其他已注册应用为 300 ms。
- 微信和云闪付另有首页过滤状态；这些细节会影响“为什么打开详情才识别”。

### 页面匹配和字段提取

页面识别与字段提取是两个注册表，不是一个正则表达式。规则包含文本完全匹配、包含、前后缀、正则、viewId、控件类型，以及组合或排除条件。

提取器以节点扁平列表为输入，支持取当前节点、前后节点、后续特定控件、跳过指定文本，以及受数量限制的向后搜索。之后进行备注清洗、缺失字段补全、金额绝对值处理及时间解析。

核心中间字段包括：金额、账单类型、备注、交易时间戳、原始时间文本、来源应用、页面类型、第一及第二账户描述、商户名称、手续费、截图路径、节点列表、账户匹配说明。这个中间对象还不是最终入库账单。

## 去重行为

存在三层不同目的的去重，不能合并成简单的“同金额不记”。

| 层级 | 已定位的判定 | 重要边界 |
| --- | --- | --- |
| 没有时间的账单 | 来源应用、类型、保留两位小数的金额、可用的备注或商户名称；已保存记录的内存缓存为一小时 | 没有可用身份文本时不走此缓存；取消不会当成成功保存写入缓存 |
| 最近事件标记 | windowId、页面类型、类型、金额，有原始交易时间时再带时间 | 对最近一次标记比较并进行原子更新；代码虽然计算耗时，但该比较分支没有基于耗时放行 |
| 数据库相似账单 | 当前用户、未删除状态、金额、对应类型条件、交易时间前后各 60 秒；无有效时间戳时用当前时间 | 当前查询未加入商户、订单号、账户或账本条件，因此“相似”不等于同一交易 |

数据库层提供三种策略：忽略并提示、弹窗确认、直接记录。其中“直接记录”策略在服务里跳过重复检查，继续进入普通记账悬浮窗，并不意味着此处直接执行数据库保存。

另一个需要处理的现有边界：悬浮窗已经显示时，`AutoBillFloatingService.o()` 没有为新识别账单建立持久队列。独立重写时应明确决定是保留这一行为，还是把它列为修复差异，不能默默丢单后声称完全等价。

## 本地账户匹配

账户匹配链按优先级从高到低尝试，只要某个匹配器返回任一账户便停止，不一定继续填满转出和转入两个账户。

| 优先级 | 匹配器 | 说明 |
| ---: | --- | --- |
| 110 | UserMappingMatcher | 有映射规则框架，但本版本读取规则的方法直接返回空列表，不能称为已可用的自定义规则功能 |
| 100 | ExactNameMatcher | 账户名称精确匹配，忽略大小写 |
| 80 | BankCardMatcher | 从付款描述提取尾号，与账户名称或备注匹配 |
| 70 | TextSimilarityMatcher | 规范化文本、字符剪枝、最长公共子串与二元组相似度，附加尾号和银行名称分数 |
| 65 | SceneMatcher | 根据微信或支付宝的场景、描述和账户名称寻找候选 |
| 60 | DefaultMatcher | 尝试名称包含微信或支付宝的默认账户 |

相似度匹配不是泛泛的“模糊匹配”：基础分数为两部分各占 0.5，尾号一致可加 0.3；短文本与长文本阈值不同，银行标识加尾号时又有阈值放宽。后续独立规则实现需要对应测试，不能只写 `contains` 冒充等效。

`cd.d` 的本地填充结果主要补账户，并没有提供与云端 AI 等价的语义分类器。原版分类选择和默认值逻辑还涉及悬浮窗的分类页面状态。

## AI 与截图分支

### 无障碍 AI 填充

1. 从节点列表抽取文字，裁剪、过滤及脱敏，提交文本限制为 4096 字符。
2. 加入账单类型、当前账本、分类候选树、账户候选和来源应用。
3. 基于用户、账本、类型、金额和文本摘要构建请求缓存键，避免重复请求。
4. 客户端调用 `emmav2/a11y2billv2`，使用返回结果补充备注、账户及分类。
5. AI 没有可用结果时回退本地账户匹配。这个回退分支已对照对应 Smali，而非只依赖反编译 Java。

进一步核对：无障碍 AI 的实际填充构建方法 `AiBillFillMode.c()` 只取账户、备注和分类，金额、时间、类型参数未由这里覆盖。不能仅凭响应数据类含有这些字段，就断言本分支实际使用了它们。AI 调用位于规则成功识别之后，也不是未知页面的通用兜底识别器。

### 分享截图记账

`OcrShareActivity` 接受 `image/*` 的分享输入，调用本地文字识别，再调用 `emmav2/ocr2bill` 生成账单草稿。APK 内包含中文与拉丁文字的 ML Kit OCR 资源，但“识别出图片文字”和“理解文字生成账单”是两个步骤，后者在这个版本中依赖服务端。

截图草稿构建方法 `com/mutangtech/qianji/auto/ocr/b.java:485` 使用金额、类型、备注、时间、分类及账户；转账还可使用手续费。类型切换使用服务端返回的置信度阈值 0.9，但这不等于置信度经过本地校准。响应结构还列有优惠和退款字段，当前检查的 `toDraft()` 并未据此证明它们被实际应用。

**仅凭 APK 无法恢复云端模型和提示词，也不能验证响应效果一致。** 本地规则替代可以保留工作流，但必须按已验证场景报告覆盖；它不是原版 AI 的等价恢复。

## 保存和账务语义

- 支出、收入、报销与转账、信用卡还款走不同构建分支。
- 需要分类的类型必须有分类；转账必须有两个不同的账户。
- 保存路径会设置账单 ID、备注、时间、账本、标签、图片和自动记账来源，写库后触发账务更新与日志。
- 原版保存路径还调用同步推送组件。本地版不能保留对原后端的调用，也不能伪造原账户的同步成功状态。
- 原模型还包含退款、报销收回、借入、借出、收款、还款及利息等类型。只实现收入支出两张表，不能满足“整款本地复刻”。

## 整款本地版范围

由 Manifest、资源和模型定位到的功能至少覆盖：

- 账本管理；收入、支出、转账、信用卡还款、退款、报销与借贷。
- 分类及子分类、标签、备注、图片、账单搜索与批量修改删除。
- 资产账户、分组排序、多币种、余额调整、资产记录与趋势。
- 月度和年度总预算、分类预算、统计图表、日历与年度汇总。
- 周期记账、分期相关来源、存钱计划及入金记录。
- 自动记账设置、权限、悬浮窗、截图入口、记录日志。
- 导入导出、主题、隐私锁、本地设置及桌面小组件。

这些是待逐项分析和验收的范围，不表示本次已经还原每项内部逻辑。涉及云端汇率、动态下载资源、原账号权益或厂商小组件接口的部分需要单独列明离线替代方案。

## 复刻验收要求

不能用“成功编译”或“看到首页”代替完成判定。最低需要建立以下证据：

1. 原版关键页面和状态截图用于核对业务能力是否遗漏；新界面单独按 Material Design 3、动态主题和真实任务 UX 验收，不追求旧界面逐像素复刻。
2. 每个可达交易规则的脱敏节点样本、预期字段、正例和反例。
3. 成功、待支付、失败、退款、重复打开、相同金额不同商户及页面变化测试。
4. 金额精度、账户余额、转账守恒、退款报销、预算统计一致性测试。
5. 无障碍权限撤销、服务重启、后台限制、悬浮窗拒绝、断网及截图失败测试。
6. 本地备份恢复及导入导出回读，证明数据不丢失。
7. 明确记录未支持场景和原版差异，不把规则数量当成识别准确率。
