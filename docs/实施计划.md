# OMyMoney 完整实施计划

状态：规格与计划已获认可，用户选择当前会话顺序实现、关键阶段独立审查。实施已开始；各任务以测试和验收记录判定完成，不以此状态说明代替实际结果。

## 目标与顺序

实现整款钱迹的独立个人本地替代品，功能以给定 APK 为参照，界面全面采用 Material Design 3 / Material You。无本地或云端 AI 实现，只保留可测试的接入接口。

整款 App 包含多个子系统，分成三份有明确交付结果的计划，而不是一次搭出大量不能操作的页面：

| 顺序 | 计划 | 独立可用的结果 |
| --- | --- | --- |
| A | [账务基础与 Material 3](计划A-账务基础与Material3.md) | 可安装的本地记账 App；账本、账户、收支转账、搜索编辑、撤销删除和备份可用 |
| B | [自动记账与 OCR](计划B-自动记账与OCR.md) | 在 A 上接入规则、去重、草稿队列、无障碍、悬浮确认、截图规则和 AI 空实现 |
| C | [完整本地功能与验收](计划C-完整本地功能与验收.md) | 补齐预算统计、退款报销借贷、多币种、周期分期、存钱计划、数据交换、隐私锁和小组件 |

执行顺序为 A -> B -> C。每份计划以独立任务的失败测试、最小实现、通过测试及审查推进。A 或 B 可用不等于整款复刻完成，最终交付必须附功能覆盖与差异清单。

## 路径与工具链

源代码工程：`PROJECT_ROOT`。按用户要求从会话临时输出目录迁入现有 OMyMoney 项目，产品名统一为 OMyMoney。规格和计划放在 `docs/`，分析与构建缓存放在忽略提交的 `work/`，APK 和验收交付放在 `outputs/`。所有计划里的代码路径均相对此工程根目录。

工程分为 `core` JVM 模块、`data` Android 数据模块、`app` Android 界面与平台模块。按功能组织文件；Android 平台实现与纯账务核心分离，但不为了分层创建过多 Gradle 模块。

已检查本机：存在 JDK 17、Android SDK 34 和 36、Build Tools 35 和 36、Android 33/34 模拟器镜像、Gradle 8.13 发行包。当前命令行默认是 JDK 25，执行时显式选择 JDK 17，不能把默认 Java 的错误误判为产品代码错误。

构建基线为 JDK 17、Gradle 8.13、AGP 8.13.2、minSdk 26、compileSdk 36、targetSdk 36。其他依赖在 A1 解析官方稳定版兼容组合并锁入版本目录和校验记录，不使用 `+`、`latest.release`、SNAPSHOT 或未固定的 Git 分支。AGP 与 Gradle/JDK 的对应关系依据[官方兼容说明](https://developer.android.com/build/releases/agp-8-13-0-release-notes)。SDK 36 的运行时测试需要补充对应模拟器镜像，不能以本机存在编译 SDK 代替运行测试。

## 跨计划约定

- 包名 `app.omymoney.android`，产品名“OMyMoney”；不与钱迹官方混淆。
- `core/model/Money.kt` 定义 `CurrencySpec(code: String, scale: Int)` 与 `Money(minor: Long, currency: CurrencySpec)`；草稿金额非负，账户分录允许有符号金额。
- `core/model/Transaction.kt` 定义 `TransactionDraft`、`Bill`、`BillKind`、`Posting`、`BillQuery`、`SaveResult`、`UndoToken`。ID 统一为 UUID 字符串，版本号为 `Long`，已保存时间用 `Instant`，账务时区用 `ZoneId`。
- `TransactionDraft` 包含账本、可空类型、可空金额、转出和转入账户、分类、备注、标签、附件引用、可空交易时间、时间来源、关联账单、手续费及排除标记；可空值允许表达未完成表单和不完整识别，不能存为 0 元成功账单。`Bill` 额外包含 ID、修订号和保存时间，类型、金额与交易时间非空。
- `BillKind` 定义 `EXPENSE, INCOME, TRANSFER, CREDIT_PAYMENT, REFUND, REIMBURSEMENT, REIMBURSED, DEBT_BORROW, DEBT_LEND, DEBT_REPAY, DEBT_COLLECT, INTEREST_EXPENSE, INTEREST_INCOME, ADJUSTMENT`。A 只启用完成验证的前三种，其余在 C 对应任务实现。
- `FieldError(field: String, code: String, message: String)` 定义在 `Transaction.kt`；核心计算入口对未完成或非法草稿抛出 `DraftValidationException(errors: List<FieldError>)`，repository 转换为 `SaveResult.Invalid`，不把异常泄漏为崩溃。
- `SaveResult` 至少区分 `Saved(billId, revision)`、`Invalid(fieldErrors)`、`Conflict(currentRevision)`；失败不得抹掉输入。
- `LedgerRepository.save(draft: TransactionDraft, expectedRevision: Long?): SaveResult` 为挂起函数；新增时版本为 null，修改时必须携带读取到的版本。
- `LedgerRepository.observeBills(query: BillQuery): Flow<List<Bill>>`、`delete(billId: String): UndoToken`、`undo(token: UndoToken): Boolean` 为统一读取与撤销边界。删除与撤销都使用数据库事务和唯一操作标记。
- 识别模块只生成草稿，通过同一保存入口入账，不维护另一份余额计算。
- `RecognitionEnhancer` 默认采用 `NoOpRecognitionEnhancer`。不引入推理引擎、模型下载、云密钥或网络请求。
- 所有 UI 文案集中为中文资源；M3 主题统一，字间距为 0，48dp 点击目标，字体放大和 TalkBack 纳入验收。
- 不申请网络权限，合并后的 Manifest 也必须检查；依赖偷偷带入的权限不得忽略。禁用系统自动云备份，用户主动本地导出另走独立流程。

## 原版证据与重写边界

只将反编译材料作为行为研究依据，不直接把整份反编译实现复制进工程。以合成或用户提供的脱敏样本建立规则测试，记录匹配顺序和字段依据。没有样本或真机验证的场景分别标为“静态还原”“样本通过”“设备通过”，禁止混成一个完成勾选。

原版的服务端 AI、账号、同步、多人协作、权益检查和动态资源服务不在本期接入。原版未接通的淘宝规则与密码页面不计入完成场景。原版广播导出、正在显示悬浮窗时丢弃新账单等行为不是必须复制的安全或体验缺陷。

## 审查重点

1. 相同金额、接近时间但属于不同商户的真实交易不能被永久吞掉：B9。
2. 键盘出现、200% 字体或返回手势不能导致保存不可达或草稿丢失：A5、A6、B11。
3. 双击保存、并发修改与进程重建不能重复扣款或回写旧余额：A3、A6、C1。
4. 损坏备份、路径穿越附件、超大或公式型 CSV 单元格不能破坏现有数据：A8、C9。
5. 无权限、未付款、空 OCR、部分时间信息必须留待人工，不得生成虚假的成功账单：B1、B10、B12。

## 计划自查

规格中的账务、平台采集、OCR、AI 预留、M3、UX、隐私、备份、统计预算及其他本地功能均有对应任务。三份计划共享上述类型和仓库接口，不另起不兼容的账单模型。每个阶段都有可运行交付；未验证的原版细节先进入证据与差异表，不用编造规则填满数量。

推荐在当前会话由同一实现者顺序执行，关键节点与最终版本再独立审查。原因是账务、识别草稿和 UI 共享的数据契约很多，先让核心闭环稳定比同时铺开大量页面更重要。也可以选择逐任务子代理实施与独立审查，代价是更多上下文和协调成本。
