Implementation and review rulings, including the user-approved TalkBack scope change. Final runtime and release evidence is recorded separately in acceptance-C.md.

Human-readable prior decisions are already committed in docs/decisions-A.md and docs/decisions-B.md. Cost if wrong: a small amount of ignored diagnostic storage, not lost implementation evidence.

Every new persisted C record family must extend export, preview validation, merge/replace, migration and round-trip tests in its own task; C9 is not permission to defer complete backup. - Ruling: plan text is the accepted local behavior contract; inspect the original APK's relevant resources/classes per task as evidence, not code to copy. Server-only or incomplete decompilation paths remain explicitly unverified and local differences are documented. - Task 1: Ruling: Original RefundPresenterImpl sends source-linked refund, timestamp, receiving asset and currency to a server; BxPresenterImpl allocates settlements chronologically with partial amounts. Independent local rules keep one source per settlement, explicit same-book/same-currency links, no copied code or server calls. Multi-source allocation is entered as separate settlements; cost if wrong: additional entry steps, documented instead of claiming exact server parity.

- Task 1: Ruling: EXPENSE refunds reduce expense up to source principal, with surplus classified separately as refund income; each refund is allocated by occurrence time then ID, retaining its own date across months. REIMBURSEMENT is an advance, not ordinary consumption; REIMBURSED is recovery, not ordinary income. Neither is included in consumption budgets. Conversion from expense to pending reimbursement keeps the original debit and category. Cost if wrong: differs from users who want unrecovered advances counted as consumption; amounts and source history remain explicit.

- Task 1: Ruling: Block source deletion or incompatible source edits while active settlements exist; require explicit confirmation to delete a settlement, with normal persisted undo. Users remove linked records before deleting a source. Undo revalidates the live graph and cannot restore an orphan or over-settlement. Cost if wrong: no single-tap cascade, but no hidden removal of financial records.

- Task 1: Ruling: UX reviewer did not independently run TalkBack, keyboard focus, or very-large-summary tests; actual compact/wide 200% screenshots only establish the shown state and automated flow. Keep the C10 device/accessibility matrix rather than claim those checks completed at C1. Cost if wrong: final acceptance may require additional UI fixes.

- Task 2: Ruling: Local liabilities have negative balances and receivables positive balances; borrowing/lending and principal settlement use two postings, interest uses a separate linked income/expense bill. Principal settlement is capped per source and must retain its principal account; independent cash accounts are allowed. The original LoanPayAct exposes separate principal/interest and saves separate records, but its sync/finish endpoints are excluded. Cost if wrong: interest is entered separately instead of an opaque combined bank payment, with no automatic interest accrual.

- Task 2: Ruling: Credit payment is a transfer, never consumption. Credit cycle settings clamp monthly days to month end and show the latest issued local cycle; a fixed due day is the first matching day after statement, or 1-90 calendar days after statement. Shared bank credit limits and bank synchronization are not inferred from offline data. Cost if wrong: banks may apply different grace periods; UI explicitly says actual bank statements govern.

- Task 2: Ruling: Groups are nullable account metadata, ordered by the first account's persisted global order; renaming applies atomically to every member including archived accounts and explicit group sorting preserves order within groups. Empty groups do not persist. Account types lock after any transaction history, preventing reinterpretation of prior debt/card postings. Cost if wrong: changing financial account type requires a new account rather than rewriting history.

- Task 2: Ruling: Balance adjustment is a positive delta with explicit increase/decrease and a required reason, saved as an ADJUSTMENT bill in the selected book. It changes balance but not ordinary income, expense or budget. The adjustment history remains editable/deleteable through the ledger. Cost if wrong: users entering an absolute target balance must calculate a delta, but opening balances and audit history are never silently rewritten.

- Task 2: Native diagnosis: repeated compact 200% adjustment-entry timeouts were not an asset-detail loading failure. Failure-only semantics and screenshot showed the New Account form: the extended floating add-account button intercepted the account row's actual center tap. A before-timeout screenshot altered timing and hid that evidence, so failure-only capture was used. Ruling: move the less-frequent asset creation action to the top toolbar with the existing accessible Add icon, keep bill creation FAB unchanged, remove unnecessary account-list bottom reservation. Cost if wrong: existing users must look to the toolbar, but scrolling account actions are no longer covered. Native acceptance remains mandatory. Additional fixture-only fixes search the lazy account selector, scroll action targets explicitly, and compare relative group order rather than assuming a pristine database.

- Task 3: Ruling: Use one explicit foreign-account exchange snapshot per bill: nominal amount retains its business currency, snapshot holds the actual gross foreign account amount, target-per-nominal rate and date. Transfers keep the paying account nominal; debt always keeps the principal account nominal; other single-cash-leg bills can record foreign settlement without relabeling recognized amounts. Linked caps remain nominal. Cost if wrong: a transaction involving two currencies both different from its nominal currency must be split, never guessed.

- Task 3: Ruling: Fees are a separate nonnegative cash-account debit on all supported kinds except balance adjustment; debt fees never reduce principal. Historical posting amounts come only from the saved snapshot, never current quotes. HALF_EVEN rounds once to the destination scale; the saved actual-minus-converted difference is disclosed, not silently posted as income/expense. Cost if wrong: fees and exchange differences may differ from bank presentation; they are explicit and editable instead of double-counted.

- Task 3: Ruling: Manual rates are directed pairs with an explicit effective date; no inferred inverse/transitive/network rates. Missing nonzero currency rates make the aggregate unavailable. Asset history is rebuilt transactionally from opening balances plus saved postings by transaction time, not a redundant daily cache; current-rate valuation is labeled as such, not historical market valuation. Cost if wrong: editing/backdating a bill revises the history, and unsupported historical market values are not invented.

- Task 4: Ruling: Month/year budgets use the book timezone and explicit budget currency; totals do not grow automatically when category limits are edited. Parent limits include children, child limits must fit a specified parent, and only non-overlapping top-level allocations count against the total. Zero is a valid explicit limit, not a deletion sentinel. Original Budget/BudgetSetNew exposes month/year/category, parent-child grouping and a deleted marker; its remote recalculation is not copied. Cost if wrong: users must explicitly increase totals before allocating more, rather than accepting the original's possible automatic adjustment.

- Task 4: Ruling: Extract shared economic facts for C4/C5: consumption/interest expenses, separate fees on every kind, chronological capped refund reductions and surplus income; transfers, principal, reimbursement advances/recoveries and adjustments do not become consumption. A record's own exclusion flag governs its facts, with budget/statistics flags independent. Refund category comes from its source and its effect retains the refund date. Cost if wrong: independently excluded source/refund records can produce a negative period usage; this remains visible rather than silently clamped.

- Task 4: Ruling: Aggregate each fact once in the requested currency: use its nominal amount when already matching, its saved actual settlement when matching, otherwise an explicit current directed manual rate. For split refunds allocate actual settlement proportionally with HALF_EVEN and assign the remainder to surplus, preserving the actual total. Missing rates suppress aggregate usage/remaining/daily values and show missing currencies. Fees stay in their own cash currency. Derived totals use BigInteger, not overflowing Long. Cost if wrong: fallback current-rate reports revalue when quotes change, so used quote dates must be disclosed; saved bills remain untouched.

- Task 4: Ruling: Persist one budget-period record per book, including deletion tombstones, in Room 7 / archive 5. Opening an eligible empty current period may copy the immediately preceding same-kind period once; any existing row, including a tombstone, prevents automatic resurrection. Explicit copying is separate and confirmed when replacing current input. Cost if wrong: prior period edits do not retroactively update copies, and a missing immediate predecessor is not guessed from older months.

- Task 4: Ruling: Existing live budgets lock their book currency and referenced category kind/parent, preventing limits being silently reinterpreted; renaming and archival remain available. Copies omit archived categories, and normal saves may retain previously budgeted archived categories. Cost if wrong: changing currency or category hierarchy requires deleting affected live budgets first rather than rewriting historical budget meaning.

- Task 4: Boundary evidence: first-year February explicit copy failed in c4-earliest-red.log because the predecessor guard rejected all of year 1. Guard narrowed to January/annual year 1 only; supported periods remain 0001 through 9998. Ruling: home always summarizes the current month and hides while list filters are active; it shares calculator/source flows with the budget page and refreshes on resume/local midnight. Cost if wrong: a filtered bill list has no budget subtotal rather than an ambiguously labeled current-month total.

- Task 5: Ruling: Statistics consumes shared C4 economic facts from complete book history, then applies one report filter (economic kind, either account, source category including children, exact tag, note substring) and values each contribution once. Summary, non-overlapping category rows, trend, calendar, annual months and contribution list reuse those values. Ordinary ledger rows still show original transactions, not a misleading sum of mixed business kinds. Cost if wrong: reports intentionally differ from raw nominal bill sums, with refunds and fees separately labeled.

- Task 5: Ruling: Date scope is an explicit month or year in the current book timezone (maximum 366 days); calendar in annual scope selects a month inside that year without changing annual totals. Empty days/months are explicit zero; missing FX remains unknown only in affected groups; signed refunds use zero-centered bars rather than misleading donut percentages. Cost if wrong: arbitrary multi-year reports require a future bounded/paged range UI.

- Task 6: Ruling: local recurrence pins the chosen timezone and original calendar anchor, with a daily/weekly/monthly/yearly interval, optional inclusive end date/count, and bounded 512-occurrence batches. java.time resolves DST gaps forward and chooses the earlier overlap offset, so an overlap is one occurrence. Month/year clipping never becomes the new anchor. Costs if wrong: no exact-second background guarantee or automatic travel-timezone reinterpretation; exceptionally long catch-up is paged.

- Task 6: Ruling: installment principal is divided in currency minor units, with the entire remainder in the final payment (100/3 = 33.33, 33.33, 33.34), not the original default first-payment remainder. Every principal payment must be positive; 1..1000 payments supported. Cost if wrong: another remainder policy requires a distinct explicit option rather than silently changing saved schedules.

- Task 6: Ruling: generated execution snapshots are immutable history. After the first occurrence, calendar/timezone/count and installment principal total are locked; recurring amounts, names and future transaction fields remain editable. A different calendar requires pausing the old plan and creating another, rather than silently moving or regenerating historical occurrences. Pause preserves the cursor; resume catches up from that cursor, with preview and confirmation required in the UI. Cost if wrong: calendar editing of an already-started plan is deliberately less permissive than creating a replacement plan.

- Task 6: Ruling: automatic execution is explicit, off by default. Expected posting validation/overflow failures become pending editable drafts with an error, never false posted receipts; storage failures roll back the entire bounded batch and remain retryable. A calendar that resolves two distinct dates to the identical instant is rejected during execution rather than silently dropping principal. Cost if wrong: exceptional skipped-calendar-day plans require manual correction; ordinary DST gap/overlap rules remain covered.

- Task 6: Review Ruling: three reported defects enter the single Important fix pass. Resume committed unpause before failed catch-up, falsely claiming unchanged data and enabling future auto-posting. Skipped failed executions still offered a now-deleted draft recovery action; regraded from Minor because financial recovery directions are false. Unidentified skip semantics/confirmation were regraded from Minor because irreversible occurrence removal cannot be verified out of row context. c6-review-red.log reproduces all three with native tests (3/7 fail). Resume and catch-up now share one transaction; pending-only recovery text and period/date/amount skip identity are implemented. Cost if wrong: storage failures retain the old paused state and the user must explicitly retry; historical failures remain stored but skipped rows no longer offer an unavailable action.

- Task 7: Ruling: savings is a progress journal, never a second ledger posting entry. Manual records explicitly affect only plan progress; linked records reference one existing ordinary transfer in the same book and count its current actual received principal in the plan currency. Each transfer can be assigned to at most one savings record across all plans. Editing/deleting a transfer updates or invalidates its contribution, visibly, rather than leaving stale progress. Cost if wrong: cross-book allocation and partial allocation of one transfer require a future explicit allocation model.

- Task 7: Ruling: fixed, increasing, reverse and target-only custom modes share exact currency minor units, bounded 1..1000 planned periods and original calendar anchors. Reverse amounts clamp at zero like the inspected baseline. Pausing blocks new records, but does not change balances or prevent correcting/removing prior records. Plan targets may be edited; currency cannot change while deposits exist. Progress totals use unbounded integers and a clamped visual fraction, retaining explicit excess. Cost if wrong: these are local plan records, not promises of actual reserved bank balances or automatic transfers.

- Task 7: Review Ruling: both P2 findings enter the single Important fix pass. Hidden manual-date validation prevented saving an otherwise valid linked deposit and could request focus on a detached input. Bottom-of-list sort failure had no visible feedback. Two new tests reproduce both assertions (c7-review-red.log). Linked dates are separate from retained raw manual input; focus requests require an attached input. Sorting failures now use a persistent, dismissible snackbar with retry without resetting scroll. Cost if wrong: invalid historical transfers retain their original legal date and contribute zero; retry re-evaluates the current ordering rather than overwriting a snapshot.

- Task 8: Ruling: use native BiometricPrompt with strong biometrics OR device credentials on API 29+, and system Keyguard credential confirmation on API 26-28. Both enabling and disabling require system authentication; no enrolled secure device means enabling is refused. Process restart/screen-off/background fail closed, rotation is not background. No custom passwords or encryption claims. Cost if wrong: old devices use a credential page rather than a fingerprint-only prompt; physical/vendor variations remain C10 boundaries.

- Task 8: Ruling: privacy mode hides widget amounts AND book names even while the app is unlocked, and disables overlays whenever privacy is enabled, including pause-to-stop. - Task 9: Ruling: Apache Commons CSV 1.14.1 and fastexcel 0.20.2 provide structured table parsing/writing; pin dependencies and verify actual Android execution. Cost if wrong: unusual provider behaviors need further evidence; this is not a blanket promise about hostile IPC or every blocked output writer. Official references: https://developer.android.com/reference/android/system/Os and https://developer.android.com/reference/android/content/res/AssetFileDescriptor.AutoCloseInputStream.
